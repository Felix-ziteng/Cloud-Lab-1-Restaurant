# 餐厅点餐系统 — 技术架构 V1

> 前置阅读：[PRD.md](./PRD.md)
> 本文档记录 V1 的架构决策及其理由，方便后续开发和未来迭代时回溯"为什么这么设计"。

## 1. 架构总览

```
┌────────────────────────────────────────────────────────────────────┐
│                     门店局域网（需连接店内 WiFi）                       │
│                                                                       │
│  顾客手机(H5)   桌台平板(N台)   前台终端(PC/平板)   KDS看板   厨房打印机   │
│       └──────────────┴───────────────┴─────────────┴──────────┘      │
│                                  │                                   │
│                          本地服务器 (mini PC)                         │
│                     Node.js + TypeScript 后端                        │
│                         PostgreSQL 数据库                            │
│                    WebSocket (Socket.IO) 实时推送                     │
└────────────────────────────────────────────────────────────────────┘
```

V1 是一个**完全本地闭环**的系统：所有终端和后端服务都部署在门店局域网内，不依赖任何云端组件运行。管理后台（店长/管理员使用）是本地服务器上的同一 Web 应用的一个视图，在前台终端或店内其他电脑上通过浏览器访问，不单独部署。

**唯一的例外**：外卖/自提自助下单这个可选模块（默认关闭），因为顾客本来就是在店外下单，天然需要一条公网入口——这条例外是精确控制、按需开启的，不影响上面这个闭环的核心结论，详见 2.8。

## 2. 关键架构决策及理由

### 2.1 本地优先（Local-First），而非纯云端

**决策**：核心业务（点餐、厨房制单、结账）全部由部署在店内的本地服务器承载，不经过公网。

**理由**：点餐系统与普通电商不同——门店 WiFi/宽带一旦中断，厨房必须仍能看到新订单、收银台必须仍能结账，不能因网络问题导致全店停摆。纯云端架构最简单，但把"店内运转"这一核心能力的可用性绑定在了外部网络链路上，风险与业务重要性不匹配。

**代价**：需要在店内部署硬件（mini PC 或同等设备），运维（备份、故障恢复）需要本地处理方案，比纯云端复杂。

**已知接受的风险**：本地优先解决的是"断网不停摆"，但不解决"断电不停摆"——本地服务器一旦断电，全店终端同时失效。V1 阶段有意不配置 UPS 不间断电源，接受这个风险，后续如有需要可再补充。

### 2.2 顾客点餐要求先连接门店 WiFi

**决策**：桌台二维码指向局域网地址，顾客需先连接门店 WiFi 才能扫码点餐，而非通过顾客自己的移动数据访问一个公网地址。

**理由**：如果顾客走的是移动数据直连云端，那么即使店内部署了本地服务器，"顾客点餐"这一步依然绕过了本地服务器，门店断网时新订单依旧无法送达店内——本地优先架构的韧性收益就被架空了。要求连接门店 WiFi 后，顾客点餐请求直接命中本地服务器，堂食全流程（点餐 → 制作 → 结账）才能真正做到不依赖公网。

**代价**：顾客体验上多一步"连接 WiFi"的操作摩擦。

### 2.3 V1 不做云端组件

**决策**：V1 阶段系统完全不包含云端后端，店长只能在店内使用管理后台查看报表、管理菜单，不支持店外远程访问。

**理由**：本地服务器已经能独立支撑门店全部运转，云端在 V1 阶段唯一的价值是"远程可视化/管理"，而这不是当前的迫切需求。引入云端会同时带来本地-云端数据同步机制、一致性处理（网络恢复后如何合并数据）等额外复杂度，与 V1 追求快速上线的目标冲突。

**后续路径**：留作快速跟进的迭代功能，届时本地服务器作为唯一事实来源（source of truth），云端只做异步的数据同步与只读汇总展示，不改变本地运行的核心逻辑。

**已确认适用范围**：预定（Reservation）功能同样遵循这条原则——V1 的预定是顾客电话或到店预约、由店员在前台录入，不支持顾客在店外自助在线预约，因此不需要任何公网可访问的入口，与其余功能一样保持完全本地闭环。若未来要支持顾客在线自助预约，需要引入一个轻量的公网可访问组件（详见 [DATA_MODEL.md](./DATA_MODEL.md) 预定相关设计），但因为预定不在点餐/厨房/结账这条关键实时链路上，即便该组件独立于本地服务器，也不会破坏"核心业务不依赖云端"的原则。

### 2.4 统一 Web 应用，而非分终端原生 App

**决策**：所有终端（顾客点餐页、桌台平板、前台终端、厨房 KDS、管理后台）是同一个 Web 应用的不同角色视图，通过浏览器访问本地服务器，按权限区分功能；V1 前台终端不集成小票打印机/钱箱/读卡器等物理外设，因此也不需要原生壳或本地桥接服务。

**理由**：所有设备都在同一局域网内访问同一后端，天然适合"一套代码库、多角色视图"的模式。相比为每个终端单独开发原生 App，Web 应用的更新只需要更新本地服务器、浏览器刷新即可全端生效，不需要应对多平台原生开发和应用商店发布流程，显著降低维护成本，更适合单人/小团队。原生/半原生方案的常见理由是浏览器对硬件外设的调用权限受限，但 V1 前台明确不需要对接这类外设，因此没有必要为此引入额外的技术栈分支。

**代价**：相比原生 App，离线缓存、推送通知、沉浸式交互能力较弱。对于局域网内固定场景的点餐系统，这些能力可以用 WebSocket 实时推送 + 后续按需升级为 PWA（支持"添加到主屏幕"、全屏 kiosk 模式、一定程度的离线缓存）来弥补。

**后续路径**：如果之后前台需要接小票打印机/钱箱/读卡器，只需要给前台这一个站点单独引入原生壳或本地桥接服务，桌台平板和顾客手机不受影响，仍保持纯网页。

顾客端进一步选择 H5 网页而非微信小程序：因为 V1 不涉及微信支付，做小程序除了增加开发和审核成本，换不来额外收益。

### 2.5 权限分级：桌台会话 / 普通店员 / 店长-管理员

**决策**：账号与会话体系分三级，而非之前设想的"顾客"与"店员"两级：

1. **桌台会话**（免登录）：桌台平板或顾客扫码进入，只能浏览菜单、加菜、查看本桌订单状态，不能查看其他桌、不能改价
2. **普通店员账号**：登录后可在前台终端完成开台/并台、代客点餐、上菜确认、正常收款、自提/配送订单核销，但**不能**改价、打折、赠菜、作废订单项，也不能编辑菜单目录价
3. **店长/管理员账号**：在普通店员权限基础上，额外拥有订单级敏感调整权限（改价/打折/赠菜/作废）、菜单目录价编辑、桌台配置、员工账号管理、报表查看

服务员与收银员两个岗位仍合并为"普通店员"一种账号类型（不按岗位拆分账号体系），但普通店员与店长/管理员之间保留权限分级。

**理由**：敏感的订单级调整和菜单目录价一旦误操作或被滥用，直接影响营收和账目可信度，需要比日常点餐操作更高的门槛。同时店内人手有限、身兼数职是常态，服务员与收银员按岗位拆分账号只会增加不必要的管理成本，与前面（V1 初版）的判断一致，因此拆分的维度从"岗位"改为"操作敏感度"。

**关联决策**：V1 不设"服务员随身设备"，任何需要普通店员或店长权限的操作统一在前台终端完成，桌台平板/顾客手机只承载免登录的点餐会话。这让权限模型保持两个物理落点（前台终端 / 桌台会话），足够覆盖三级账号，不需要为"移动中的店员"单独设计一套设备和会话管理。

### 2.6 厨房出品：电子看板 + 自动打印小票

**决策**：新订单同时推送到 KDS 电子看板和厨房小票打印机；后厨在看板上点击"完成"来更新订单状态，纸质小票作为出品流转的实物凭证，两者并存而非二选一。

**理由**：如果只打印小票、没有任何数字化的状态反馈入口，"制作中/已完成"这个状态就无法回传系统——而这个状态是要实时同步给前台、给顾客看"预计还要多久"的，是订单状态机里关键的一环，纯打印会让这部分实时性设计失效。如果只用电子看板不打印，则要求后厨完全脱离已经习惯的纸质小票工作方式，对已有习惯的后厨团队是额外的适应成本。看板 + 打印并存的方案能同时保留状态回传能力和后厨熟悉的实物流转方式，是餐饮 SaaS（如二维火、客如云等）的主流做法。

**代价**：比单一方案多一套硬件（既要看板屏幕又要打印机），成本和维护点更多。

**后续修订**：这条决策是面向单一客户定制时定的。产品化之后（见 2.7），"要不要打印机、打印机摆哪"改成了按客户配置，不再是所有部署都强制的硬性组合。

### 2.7 产品化：用运行时配置覆盖客户差异，而不是代码分支

**背景**：项目从"只服务一家餐厅"转向"同一套代码卖给多个客户，每家的硬件/功能取舍不同"（比如有的客户只要顾客自己扫码，不配桌台平板；有的要后厨打印机，有的只要电子看板；有的不需要外卖/预定模块）。

**决策**：新增 `StoreConfig`（门店能力配置，单店部署下是固定单行）作为运行时开关，而不是给每个客户单独出一个代码分支或定制构建：

- `kdsScreenEnabled` / `deliveryEnabled` / `reservationEnabled` 三个开关，决定这份部署要不要暴露厨房看板、外卖、预定这几个可选模块
- 后端用 `FeatureEnabledGuard` + `@RequireFeature(...)` 整体挡掉未开启模块的接口；前端启动时拉一次配置，没开的模块入口直接不渲染
- 桌台平板 vs 纯顾客扫码这一维度**不需要**配置开关——见 2.4，两者本来就是同一套代码的同一个入口，只是硬件采购决策，不需要软件感知

**理由**：新客户上线应该是"部署同一个安装包 + 勾选这家店要哪些能力"，而不是拉分支改代码——后者会导致维护成本随客户数量线性甚至更快增长，是我们明确要避免的。核心业务骨架（数据模型、订单状态机、三级权限模型）是所有客户通用的，差异只体现在"该不该暴露某个模块入口"这个薄薄一层。

**代价**：多一张配置表和一层守卫逻辑；每新增一个可选模块，都要记得同时在后端加 `@RequireFeature` 和前端加条件渲染，否则开关形同虚设（比如外卖订单可以从 `/orders` 通用入口创建，不只是 `/orders/:id/delivery/*` 专属接口，两处都要挡）。

**打印代理程序（Printer Agent）**：2026-08-20 已实现，见 `apps/print-agent`——一个独立于主 backend 的本地 Node.js 进程，不是 NestJS 模块（打印机驱动问题/崩溃不该拖垮点餐/厨房这些核心功能，也方便以后单独部署到离打印机更近的设备上）。落地方式：

- 后端新增 `PrintJob` 队列表（`type: kitchen | receipt`，`payload` 是建单/收款那一刻的快照，不是实时反查订单）。`submitRound`/`createStandaloneOrder` 触发厨房小票任务，`recordPayment` 触发收据任务
- 打印代理通过 `kitchen` WebSocket 房间订阅 `print_job_created` 即时通知，同时定期轮询 `GET /print-jobs/pending` 兜底补漏（WS 通知是"发了就忘"，代理离线期间产生的任务靠轮询补上）；处理完通过 `PATCH /print-jobs/:id` 回报成功/失败
- 打印代理不是店员账号，用固定共享密钥（`PRINT_AGENT_TOKEN`）鉴权，不走 JWT/PIN 登录那一套——它是无人值守服务，没有界面弹窗提示"请重新登录"
- 具体品牌的 ESC/POS 差异抽象成统一的 `Printer` 接口（`printKitchenOrder`/`printReceipt`/`testPrint`/`getStatus`），当前只有 `EpsonPrinter`（基于 `node-thermal-printer`，适配 TM-T82III 网口+无线版）是真正可用的实现，`StarPrinter`/`BixolonPrinter` 是占位适配器，等有客户用这些品牌再补
- **已知限制**：本地没有实体打印机，ESC/POS 指令生成、字符集（中文用 `CharacterSet.CHINA`）、网口连接这几个环节只验证到"代码逻辑正确、连接失败时能正确捕获错误并回报"，没有验证过真机出纸效果——硬件到位后需要专门测一轮

`StoreConfig` 暂时还没加打印相关的配置字段（比如"要不要打印小票"这种开关），当前是只要 `apps/print-agent` 这个进程连着就会打印，没连就任务积压在队列里等着；如果之后要支持"这家店不装打印机"这种客户，需要在 `StoreConfig` 里补一个开关，跳过打印任务的创建。

### 2.8 外卖/自提自助下单：在"本地优先"上开一个精确控制的口子，而不是放弃这条原则

**背景**：2.7 的产品化把外卖/自提自助下单做成了一个可选模块（`deliveryEnabled`），但这个模块有个 2.1-2.3 定架构基线时没预见到的特性——顾客是在店外下单的。2.2 的决策（顾客点餐必须先连门店 WiFi）能保证堂食顾客走本地服务器，但外卖顾客压根不在店里，手机连的是自己的移动网络，这条路径天然绕不开公网，不是"要不要"的问题，是这个业务场景本身决定的。

**决策**：不引入云端后端（不违反 2.3），而是给本地服务器开一个"精确控制"的公网入口：

- 本地新增一个反向代理（`ops/Caddyfile` + `docker-compose.yml` 的 `caddy` 服务），只放行外卖/自提顾客用得到的那几个接口（菜单、自助下单、订单查询/找回、WebSocket）+ 前端静态文件，白名单之外的 `/api/*` 一律 404——前台/厨房/收银/店员登录这些接口完全碰不到这个公网入口，物理上不经过它
- 公网访问这个反向代理靠 Cloudflare Tunnel（`cloudflare/cloudflared`）：本地主动发起一条出站连接换取公网地址，不需要在路由器开端口、不需要固定公网 IP，店内网络断了这条隧道自然也断（外卖自助下单本来就用不了了，但堂食/厨房/收银这些核心链路完全不受影响，因为它们从来不走这个代理）
- 当前只验证过免费的临时隧道（地址每次重启都变），正式给客户用之前需要客户提供域名、换成 Cloudflare 命名隧道（固定地址），并且**必须先把 `JWT_SECRET`/数据库密码从开发默认值换成真实随机值**——见 `docs/OPTIONAL_MODULES.md` 的启用步骤

**理由**：反向代理的白名单是关键——如果公网入口直接怼到 backend 本身，那么"本地优先"在事实上就名存实亡了（任何接口都可能被公网访问到，只是靠权限校验兜底）。这里选择的做法是从网络拓扑层面就切断公网到店员/厨房接口的物理路径，权限校验是第二道防线，不是唯一防线。反向代理本身不引入云端存储/计算，数据和业务逻辑仍然 100% 在本地服务器上，只是流量的"进店"路径多了一条，符合 2.3 里"云端只做异步的数据同步与只读汇总展示，不改变本地运行的核心逻辑"这条原则的精神——这里甚至比那个更保守，公网连计算和存储都不碰，只转发几个白名单接口。

**代价**：多一层反向代理配置，新增一个可选接口都要记得同时改白名单，否则要么漏掉真该开放的接口、要么不小心开放了不该公开的接口；免费临时隧道地址不固定，不适合印在外卖二维码/菜单上给顾客长期使用，需要客户自己的域名才能真正稳定使用。

**现状（2026-08-20）**：这套反向代理和隧道基础设施是搭好的，但外卖/预定模块本身默认关闭（见 `StoreConfig` 迁移 `20260820083327_store_config_default_off`），Caddy 容器也停着——只有客户明确需要外卖自助下单时才会一起启用，见 `docs/OPTIONAL_MODULES.md` 的具体启用步骤。

## 3. 硬件与部署拓扑

| 站点 | 数量 | 形态 | 说明 |
|---|---|---|---|
| 本地服务器 | 1 台 | mini PC（常驻运行） | 承载后端服务、数据库，是全店唯一的运行主体 |
| 前台终端 | 1 台（起） | PC 或平板，浏览器/PWA | 普通店员与店长/管理员登录站点，承载 POS 收单、订单调整、管理后台 |
| 桌台平板 | N 台，按同时可服务桌数配置 | 平板，浏览器/PWA 全屏 kiosk 模式 | 出厂固定绑定桌号（或店员分发时指定），与顾客扫码共享同一桌台会话；固定装配还是机动分发由现场运营决定，不影响软件设计 |
| 顾客手机 | BYOD，无需采购 | 手机浏览器 H5 | 需连接门店 WiFi 后扫码进入对应桌台会话；空闲桌台首次扫码即自动开台，无需店员先操作（详见 [API_DESIGN.md](./API_DESIGN.md)） |
| 厨房 KDS 看板 | 1 台（起，可按出品站点扩展） | 平板/显示屏，浏览器全屏 | 展示订单队列，点击标记完成 |
| 厨房小票打印机 | 1 台（起，可按出品站点扩展） | 热敏小票打印机 | 新单自动打印，供后厨物理流转 |

**网络要求**：门店 WiFi 覆盖用餐区（顾客手机、桌台平板）和厨房；本地服务器、前台终端、KDS 看板建议有线连接以获得最稳定的连接质量，桌台平板无线连接。

## 4. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 后端语言/框架 | Node.js + TypeScript | 前后端共享类型定义，减少接口契约不一致的低级 bug；WebSocket 生态（Socket.IO）成熟；小团队/单人开发效率高；mini PC 上资源开销可控 |
| 数据库 | PostgreSQL | 多终端并发写入（多桌同时下单、厨房同时改状态）需要可靠的事务保证；未来若加云同步或多店支持，迁移成本比 SQLite 低 |
| 实时通信 | WebSocket（Socket.IO） | 订单状态、厨房队列、桌台状态需要毫秒级推送到相关终端，轮询体验明显更差 |
| 前端 | React + TypeScript + Vite | 生态成熟，组件化适合"同一套代码、多角色视图"的场景 |
