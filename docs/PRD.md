# 餐厅点餐系统 — 产品需求文档（PRD）V1

> 状态：V1 基线已确认，作为后续详细设计与开发的依据。
> 范围：单店。

## 1. 背景与目标

从零设计一套商业级餐厅点餐系统，覆盖堂食扫码点餐、外卖自提/自营配送、收银台代客点餐三种业务场景，V1 面向单店部署。

## 2. V1 业务范围

### 2.1 包含的业务场景

| 入口 | 说明 |
|---|---|
| 堂食扫码点餐 | 顾客连接门店 WiFi 后扫桌台二维码点餐；含开台、并台、预定的桌台管理 |
| 外卖 / 自提 | 顾客线上下单，可选择「到店自提」或「自营配送」（餐厅自有人力配送，非第三方平台） |
| 收银台 / POS 点餐 | 店员为到店顾客代客下单，走与堂食相同的订单管道 |

### 2.2 V1 明确不做（范围外，留作后续迭代）

- **在线支付网关集成**（微信支付/支付宝）：V1 仅支持到店/柜台支付；自营配送订单为骑手上门货到付款（现金或顾客扫骑手个人收款码），系统只记录"已收款"状态，不经手实际资金
- **会员 / 储值 / 优惠券等营销体系**
- **第三方外卖平台对接**（美团、饿了么等）
- **多门店 / 连锁架构**：V1 只服务单店，数据模型和部署不考虑跨店场景
- **云端远程管理**：店长仅在店内使用管理后台，不支持店外远程查看报表/改菜单（见 ARCHITECTURE.md 中的网络架构决策）

## 3. 用户角色

| 角色 | 职责 |
|---|---|
| **顾客**（桌台会话，免登录） | 通过桌台平板或自行扫码（连接门店 WiFi 后）点餐、加菜、查看订单状态；外卖/自提场景下线上下单 |
| **普通店员**（服务员 + 收银员合并为单一账号类型） | 开台/并台/预定、前台代客点餐、上菜确认、发起结账、POS 收款、开票、自提/配送订单核销 |
| **厨房 / 后厨** | 通过 KDS 看板接单，订单状态流转：待处理 → 制作中 → 已完成（自动同步打印小票） |
| **配送员** | 自营配送订单的接单、取餐、配送状态更新、上门收款确认 |
| **店长 / 管理员** | 菜单与价格管理（含目录价编辑）、订单级敏感操作（改价/打折/赠菜/作废）、桌台配置、员工账号管理、报表查看 |

> 决策记录：服务员与收银员的职责边界模糊、人员经常兼任，因此合并为单一"普通店员"账号类型，不拆分成两个独立账号体系。但普通店员与店长/管理员之间**保留权限分级**：日常操作（点餐、上菜、正常收款）普通店员账号即可完成；改价、打折、赠菜、作废等订单级敏感调整，以及菜单目录价编辑，仅限店长/管理员账号——这是因为敏感操作一旦误操作或滥用，直接影响营收和账目可信度，需要更高的操作门槛。V1 不设"服务员随身设备"，任何需要店员操作的场景统一在前台终端完成。

## 4. 核心业务流程

三个点餐入口最终汇入**同一条订单状态机**——无论订单来自堂食扫码、线上下单还是店员代客下单，后厨和收银看到的都是同一种订单对象，这是系统的核心设计原则。

```
[点餐: 堂食扫码 | 外卖线上下单 | 店员代客下单]
        ↓
[厨房接单/制作] (KDS: 待处理 → 制作中 → 已完成)
        ↓
[交付: 堂食上菜 | 到店自提核销 | 骑手配送]
        ↓
[结账/收款: 堂食柜台收款 | 自提柜台收款 | 配送货到付款(骑手确认)]
        ↓
[订单关闭]
```

### 4.1 堂食扫码点餐

1. 店员开台（选定桌台，状态变为「占用」），或顾客自行连接门店 WiFi 扫桌台二维码
2. 顾客浏览菜单、加入购物车、提交点餐（支持同一桌台多次追加点餐）
3. 订单进入厨房 KDS 队列，状态流转：待处理 → 制作中 → 已完成
4. 店员确认上菜
5. 顾客或店员发起结账，店员在 POS 端完成柜台收款
6. 订单关闭，桌台状态变为「待清台」，清台后回到「空闲」

桌台生命周期：`空闲 → 占用（开台/并台）→ 待清台 → 空闲`，支持预定。

### 4.2 外卖 / 自提

1. 顾客线上下单，选择「到店自提」或「自营配送」
2. 订单进入厨房制作队列
3. **自提**：顾客到店，店员核销订单并收柜台款
   **配送**：分配骑手 → 骑手取餐 → 配送中 → 送达，骑手上门收款（货到付款）并在系统中确认「已收款」
4. 订单关闭

### 4.3 收银台 / POS 代客点餐

等同堂食流程，区别仅在于下单发起人是店员而非顾客本人扫码，订单汇入同一管道。
